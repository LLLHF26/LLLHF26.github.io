MyBatis 详解：从核心原理到 MyBatis-Plus 实战全指南

发表于 2026-07-25 分类于 学习笔记

MyBatis 是国内 Java 后端最流行的持久层框架，没有之一。本文从 JDBC 原始开发的痛点出发，层层深入 MyBatis 的核心架构与工作流程（SqlSessionFactory → Executor → StatementHandler → ResultSetHandler 全链路），详解 Mapper 映射、动态 SQL、一二级缓存、插件拦截器机制，再到 MyBatis-Plus 的条件构造器、分页、自动填充、逻辑删除、乐观锁等增强能力，最后梳理 2026 年最新版本特性（MyBatis 3.5.19/MyBatis-Plus 3.5.17/GraalVM Native Image）、生产级优化指南和高频面试题。读完这篇文章，你对 MyBatis 的理解将从”会用”升级到”精通”。

MyBatis 详解：从核心原理到 MyBatis-Plus 实战全指南

JDBC 的痛点非常直观：

痛点 具体表现

一句话总结：JDBC 的代码有 80% 都是重复的”仪式性代码”，真正的业务逻辑只占 20%。

2、ORM 框架的演进路线

Java 持久层框架的发展经历了三个阶段：

  • Spring JdbcTemplate：帮我们管理了 Connection 的获取与释放，使用 RowMapper 做结果映射，写法比原生 JDBC 简洁很多。但它仍然需要手写 SQL 字符串，动态 SQL 依然是一堆 StringBuilder。
  • Hibernate：全自动 ORM，通过 HQL 和对象关系映射自动生成 SQL，开发者不需要写一行 SQL。但代价是学习曲线陡峭、复杂查询性能难以控制、N+1 查询问题。
  • MyBatis：半自动 ORM —— 开发者自己写 SQL，框架帮你做参数映射、结果映射、连接管理。保留了 SQL 的灵活性，又消灭了 JDBC 的模板代码。

MyBatis 的核心理念是 “SQL 是第一公民”。它不生成 SQL，不隐藏 SQL，而是让你用最舒服的方式写 SQL。

二、MyBatis 核心架构：三层设计

MyBatis 的功能架构可以分为清晰的三层：

接口层：对外暴露两种使用方式 —— 传统的 SqlSession API（sqlSession.selectOne("namespace.id", param)）和 Mapper 接口代理（userMapper.selectById(1L)）。现代开发几乎只用后者。

数据处理层：MyBatis 的核心。负责参数映射（#{} → PreparedStatement 占位符、${} → 字符串替换）、动态 SQL 解析（<if>/<foreach>/<where> 等标签）、SQL 执行（通过 Executor 交给 JDBC）、结果映射（ResultSet → Java 对象/Map）。

基础支撑层：提供连接池（默认 PooledDataSource）、事务管理（JDBC/MANAGED）、配置加载（XML 解析为 Configuration 对象）、缓存支持（一级缓存/二级缓存）。

2、#{} vs ${}：面试必考

这是 MyBatis 最经典的问题之一，很多人即便用过也未必能说清楚本质区别：

对比维度 #{} ${}
原理 预编译占位符（?） 字符串直接拼接
SQL 注入 安全（自动转义） 不安全（无转义）
使用场景 WHERE 条件值、INSERT/UPDATE 的字段值 动态表名、动态列名、ORDER BY 字段名、LIKE 模糊匹配（需拼接 %）
类型处理 TypeHandler 自动转换 无类型处理，直接拼字符串

黄金法则：能用 #{} 的地方绝不用 ${}。只有当你确实需要让 SQL 本身发生变化（如表名、列名、排序字段）时，才用 ${}，且必须对参数做白名单校验。

3、ResultMap：解决字段映射的终极方案

association vs collection 本质区别：

  • association：一对一/多对一，返回单个对象。使用 javaType 指定类型。
  • collection：一对多，返回集合。使用 ofType 指定集合元素类型。

六、MyBatis 缓存机制

1、一级缓存（Local Cache）

默认开启，SqlSession 级别，无法关闭（只能控制作用域）。

一级缓存失效的场景：

  • 不同的 SqlSession
  • 同一个 SqlSession 但查询条件不同
  • 同一个 SqlSession 执行了 INSERT/UPDATE/DELETE（会清空缓存）
  • 手动调用了 sqlSession.clearCache()

坑点：Spring 整合 MyBatis 时，每次请求 SqlSession 都不一样（Spring 管理的 SqlSession 是请求级别的），所以一级缓存在 Spring 环境下基本上没用。不要指望它能提升性能。

2、二级缓存（Second Level Cache）

默认关闭，需要手动开启。Namespace 级别，跨 SqlSession 共享。

二级缓存工作原理：

二级缓存的注意事项（踩坑清单）：

  • 返回的对象必须实现 Serializable（因为二级缓存需要序列化存储）。
  • 多表关联查询可能读到脏数据（别的 Namespace 更新了关联表，但本 Namespace 的缓存没有失效）。
  • 生产环境中谨慎使用：分布式场景下 MyBatis 二级缓存无法同步，推荐用 Redis 等外部缓存。
  • 适合：读多写少、数据变化不频繁的字典表、配置表。

十一、MyBatis vs JPA/Hibernate：如何选型？

维度 MyBatis JPA/Hibernate
定位 半自动 ORM（SQL 第一公民） 全自动 ORM（对象第一公民）

十二、高频面试题

Q1：MyBatis 的工作原理是什么？

MyBatis 通过 SqlSessionFactoryBuilder 加载配置文件构建 SqlSessionFactory，每次数据库操作从 Factory 获取 SqlSession。SqlSession 内部通过 Executor 执行 SQL，Executor 委托 StatementHandler 创建 JDBC Statement，由 ParameterHandler 设置参数、ResultSetHandler 处理结果映射。Mapper 接口通过 JDK 动态代理创建代理对象，方法调用时由 MapperProxy 拦截并路由到对应的 MappedStatement。

Q2：#{} 和 ${} 的区别是什么？

#{} 是预编译占位符，MyBatis 将其替换为 ?，通过 PreparedStatement 的 setXxx() 方法安全传参，天然防 SQL 注入。${} 是字符串直接拼接，不具备防注入能力。#{} 用于 WHERE 条件值，${} 仅在需要动态改变 SQL 结构（如表名、列名、ORDER BY 字段）时使用，且必须配合白名单校验。

Q3：MyBatis 的一二级缓存有什么区别？

一级缓存是 SqlSession 级别的，默认开启，生命周期与 SqlSession 绑定。二级缓存是 Mapper（Namespace）级别的，需要手动配置开启，跨 SqlSession 共享，需要实体类实现 Serializable。在 Spring 整合环境中，一级缓存基本无效（每次请求有不同的 SqlSession）。分布式环境不推荐使用 MyBatis 二级缓存，建议用 Redis 等外部缓存。

Q4：MyBatis 的插件机制能拦截哪些对象？原理是什么？

能拦截四大核心对象：Executor、StatementHandler、ParameterHandler、ResultSetHandler。原理是责任链模式 + JDK 动态代理：每个插件通过 @Intercepts 注解声明拦截目标，MyBatis 初始化时为目标对象生成代理，调用时经过插件链的层层拦截。分页插件（PageHelper / PaginationInnerInterceptor）就是通过拦截 Executor 的 query 方法实现的。

Q5：MyBatis-Plus 的逻辑删除原理是什么？

在实体类字段上加 @TableLogic 注解。执行 deleteById() 时，MP 不会生成 DELETE 语句，而是生成 UPDATE SET deleted = 1 WHERE id = ? AND deleted = 0。执行 SELECT 查询时，MP 自动在 WHERE 条件后追加 AND deleted = 0，对开发者完全透明。

Q6：如何解决 MyBatis 中实体类字段名与数据库字段名不一致的问题？

三种方案：① 在 settings 中设置 mapUnderscoreToCamelCase=true（驼峰自动映射）；② 在 SQL 中使用 AS 别名：SELECT user_name AS userName FROM ...；③ 使用 <resultMap> 显式指定 column → property 的映射关系。

Q7：MyBatis 批量插入有哪几种方式？哪种最好？

三种方式：① <foreach> 拼接单条 INSERT 多行 VALUES — 简单但 SQL 过长时有性能问题；② BatchExecutor 模式 — 推荐，JDBC 批量提交，性能最优；③ MyBatis-Plus 的 saveBatch() — 最方便，底层用批量提交，推荐日常使用。

Q8：为什么 Spring 整合 MyBatis 后一级缓存失效？

Spring 管理 SqlSession 的生命周期为”请求级”：每次请求开启一个新 SqlSession，请求结束关闭。而一级缓存是 SqlSession 级别的，跨 SqlSession 无法共享。所以 Spring 环境下，即便同一个请求内多次调用同一个 Mapper 方法，也会每次都查数据库（如果不在同一个事务内）。解决方案：使用 @Transactional 确保同一事务内复用同一个 SqlSession，此时一级缓存仍有效。

十三、总结

MyBatis 之所以能成为国内 Java 后端的事实标准，核心在于它尊重 SQL——不隐藏、不生成、不黑盒。开发者保留了对 SQL 的完全控制权，同时 MyBatis 帮你消灭了 JDBC 的模板代码。而 MyBatis-Plus 在此基础上更进一步，让单表 CRUD 几乎可以不写一行 SQL。

2026 年，MyBatis 生态的三大趋势值得关注：GraalVM Native Image 支持（编译为原生二进制，毫秒级启动）、虚拟线程（提升高并发场景下的数据库吞吐量）、以及 DSL 重构（Java 17+ 的现代化代码风格）。对于后端开发者来说，深入掌握 MyBatis 的原理和 MyBatis-Plus 的运用，是面试和日常开发的必备技能。
