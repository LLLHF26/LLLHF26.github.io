Elasticsearch 搜索引擎详解：从倒排索引到向量检索与 9.x 新特性

一、为什么需要 Elasticsearch？关系型数据库的搜索困境

很多初学者的第一个疑问是：「MySQL 也有 LIKE 模糊查询和 FULLTEXT 索引，为什么还要引入 Elasticsearch？」答案藏在两种数据库截然不同的底层数据结构中。

1.1 关系型数据库做搜索的三大硬伤

维度 MySQL LIKE '%keyword%' Elasticsearch 全文检索
索引利用 前缀通配 %keyword 无法走 B+ 树索引，全表扫描 倒排索引直接定位包含关键词的文档，O(1) 查找
相关性排序 只能按字段排序，无法按匹配程度打分 BM25 算法计算 TF-IDF 相关性分数，最相关的排最前
分词能力 FULLTEXT 分词弱，中文需 ngram 插件，灵活性差 内置 40+ 分词器、IK/Pinyin 等插件，支持自定义分析器链
聚合分析 GROUP BY 在亿级数据上性能急剧下降 预计算 + 列式存储（Doc Values），亿级数据秒级聚合
水平扩展 分库分表复杂，跨分片搜索困难 天然分布式，分片+副本自动路由，可线性扩展到 PB 级

1.2 典型应用场景

一句话总结：MySQL 是「精确匹配 + 事务」的专家，Elasticsearch 是「模糊搜索 + 聚合分析」的专家。两者不是替代关系，而是互补——生产中常见的模式是 MySQL 存主数据，Elasticsearch 做搜索副本。

二、倒排索引：Elasticsearch 的核心数据结构

倒排索引（Inverted Index）是 Elasticsearch 全文检索的基石。理解它，就理解了 ES 80% 的核心。

2.1 正排索引 vs 倒排索引

正排索引（传统 B+ 树）：文档 → 词

要搜 “search”，必须逐个扫描每篇文档——这是 LIKE 的做法。

倒排索引：词 → 文档

搜 “search”，直接查倒排表得到 [1, 3]，无需扫描文档。

FST（Finite State Transducer）是 Lucene 用于存储词典的核心数据结构。它将所有词项组织成一棵前缀共享 + 后缀共享的有向无环图：

2.5 近实时搜索原理：Segment + Refresh

Elasticsearch 不是实时搜索引擎，而是近实时（Near Real-Time, NRT），默认 1 秒延迟。原理如下：

概念 说明 默认值
Refresh 内存 Buffer → 新 Segment，使文档可搜索 1 秒
Flush Segment fsync 到磁盘 + 清空 Translog 30 分钟或 Translog 512MB
Translog 写前日志，保证 Flush 前崩溃可恢复 每笔写入后 fsync（可调）
Segment Lucene 最小索引单元，不可变 合并策略：Tiered Merge Policy
Merge 多个小 Segment 合并成大 Segment 后台线程自动执行

关键洞察：Segment 不可变意味着更新 = 标记旧文档删除 + 写入新文档。这也是 ES 不适合高频更新的原因——每次更新都会产生新的 Segment，最终靠 Merge 合并清理。

7.2 分片（Shard）与路由

每个索引被分成多个主分片（Primary Shard），每个主分片有零到多个副本分片（Replica Shard）：

分片数量决策——生产中最关键的架构决策之一：

因素 建议
单分片大小 30GB ~ 50GB（搜索性能与恢复速度平衡）
分片数量 索引创建后不可修改（只能 reindex），需提前规划
节点分片数 每节点不超过 20 个分片（堆内存限制）
副本数量 生产至少 1 副本；搜索压力大可 2+ 副本
数据增长 按时间 rollover（如 logs-2026.07.28）

分片过少的后果：无法水平扩展，单分片过大导致恢复慢。
分片过多的后果：每个分片消耗资源（内存、文件句柄），过多小分片浪费资源且查询扇出（Fan-out）开销大。

7.3 写入流程：Primary → Replica

写入一致性参数（wait_for_active_shards）：

值 语义 适用场景
1 只要 Primary 可用就写 最高写入吞吐，最低安全性
quorum 多数分片可用才写 平衡（默认）
all 所有分片（含副本）都可用才写 最高安全性，最低可用性

7.4 搜索流程：Scatter-Gather

关键洞察：搜索需要查询所有分片（Scatter），这就是为什么分片过多会降低查询性能——每个查询的扇出开销线性增长。但分片过少又无法水平扩展，需要平衡。

十、性能优化：索引速度 + 搜索速度

10.1 索引速度优化

优化项 方法 效果

十二、高频面试题

Q1：Elasticsearch 为什么比 MySQL LIKE 快？

答：核心区别在数据结构。MySQL LIKE '%keyword%' 无法利用 B+ 树索引（前缀通配），只能全表扫描，时间复杂度 O(N)。Elasticsearch 使用倒排索引，通过 FST 词典 O(词长) 定位词项，再通过 Posting List 直接获取包含该词的文档列表，时间复杂度接近 O(1)。此外，ES 的 BM25 评分能按相关性排序，而 MySQL 只能按字段排序。

Q2：倒排索引的底层结构是什么？为什么用 FST？

答：倒排索引由三层组成：(1) Term Dictionary 用 FST（有限状态机）存储所有词项，前缀和后缀共享，百万级词项仅占几十 MB 内存，查找 O(词长)；(2) Posting List 用 FOR 增量编码 + Roaring Bitmap 压缩文档 ID 列表；(3) Doc Values 列式存储字段值，用于聚合和排序。FST 相比 HashMap 节省 10 倍以上内存，且天然支持前缀查询。

Q3：Elasticsearch 的近实时原理是什么？如何实现真正实时？

答：ES 写入文档时先写 Translog（持久化日志）再写 In-Memory Buffer。默认每 1 秒 Refresh 一次，将 Buffer 生成新的 Segment 进入 OS Page Cache 变为可搜索——这就是 1 秒近实时延迟的原因。要实现真正实时，可在写入后调用 POST /index/_refresh 手动刷新，但会牺牲写入吞吐量。或者使用 ?refresh=wait_for 参数等待下次自动 refresh。

Q4：如何选择分片数量？分片过多或过少有什么问题？

答：分片数量在索引创建后不可修改（只能 reindex），需提前规划。经验法则：单分片 30-50GB，分片数为数据节点的 1-3 倍。分片过少：无法水平扩展、单分片过大恢复慢、热点风险。分片过多：每个分片消耗资源（堆内存、文件句柄、CPU），搜索需要查询所有分片（Scatter-Gather 扇出开销），过多小分片浪费资源。时间序列数据可通过 ILM + Rollover 动态管理。

Q5：BM25 和 TF-IDF 有什么区别？k1 和 b 参数怎么调？

答：TF-IDF 的词频线性增长，长文档和高频词得分虚高。BM25 引入了饱和函数（k1 控制）和文档长度归一化（b 控制）。k1 默认 1.2，值越大词频影响越大，适合标题等短字段可调到 2.0。b 默认 0.75，值越大长文档惩罚越强，设为 0 则不考虑文档长度。生产中一般用默认值，特殊场景微调。

Q6：filter 和 must 有什么区别？为什么 filter 更快？

答：must 参与 BM25 评分且不缓存；filter 只判断是否匹配不评分，且结果自动缓存为 Bitset。Filter 更快有两个原因：(1) 跳过评分计算（BM25 涉及多次浮点运算）；(2) Bitset 缓存命中时直接跳过倒排表查找。对同一 filter 条件的重复查询，第二次可能快 10 倍以上。生产中能用 filter 的场景绝不用 must。

Q7：Elasticsearch 如何做深度分页？from/size、scroll、search_after 的区别？

答：from + size 限制 10000，深翻页时每个分片需取 from + size 条排序，协调节点合并 N×(from+size) 条——深度越大越慢。scroll 创建快照游标，适合批量导出但不适合实时搜索（数据非实时）。search_after 利用排序字段值作为游标，每次只取 size 条，无状态、实时、无深度限制，是生产推荐的深分页方案。9.x 推荐使用 PIT（Point in Time）+ search_after，保证结果一致性。

Q8：向量检索和传统全文检索有什么区别？什么是混合检索？

答：全文检索基于倒排索引和 BM25 评分，擅长精确关键词匹配但存在语义鸿沟（同义词、跨语言等）。向量检索将文本编码为高维向量，在向量空间中计算余弦相似度，能理解语义但可能丢失精确匹配能力。混合检索同时执行 BM25 和 kNN 搜索，通过 RRF（Reciprocal Rank Fusion）融合排名，兼顾精确性和语义性——这是 RAG 系统的标准实践。Elasticsearch 9.x 原生支持混合检索 API。
