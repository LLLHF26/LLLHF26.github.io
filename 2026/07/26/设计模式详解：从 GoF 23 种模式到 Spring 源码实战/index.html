设计模式详解：从 GoF 23 种模式到 Spring 源码实战

发表于 2026-07-26 分类于 学习笔记

设计模式是面向对象设计的”棋谱”，更是后端面试的超高频考点。本文从六大设计原则出发，系统梳理 GoF 23 种设计模式（创建型 5 + 结构型 7 + 行为型 11），每种模式配有 UML 意图说明、Java 实战代码、Spring/JDK 源码落地案例，再延伸到 2026 年 AI Agent 设计模式新趋势（ReAct / Plan & Execute / Multi-Agent / Reflection），最后附 10 道高频面试题与生产避坑清单。读完本文，你对设计模式的理解将从”背概念”升级到”能设计、能落地、能讲透”。

设计模式详解：从 GoF 23 种模式到 Spring 源码实战

一、设计模式是什么？为什么每个后端都要学？

1、一句话定义

设计模式（Design Pattern）是针对软件设计中反复出现的问题，总结出的一套可复用的解决方案模板。

它不是发明，而是发现——是前辈们在无数项目踩坑后提炼出的经验结晶。1994 年，GoF（Gang of Four）在《Design Patterns: Elements of Reusable Object-Oriented Software》一书中正式收录了 23 种设计模式，奠定了面向对象设计的基础。

2、为什么必须学

维度 不学设计模式 学了设计模式
代码质量 if-else 堆砌，改一处动全身 职责清晰，扩展开放
沟通成本 “你那个类这样写不太好” “这里用策略模式替换掉 if-else”
面试表现 只能说”我用了 Spring” “Spring 的 AOP 用了动态代理模式”
读源码 看 Spring/JDK 像看天书 一眼识别模式，快速理解设计意图
架构能力 遇到新需求无从下手 自然映射到合适的模式

3、23 种模式全景图

GoF 23 种设计模式按职责分为三大类：

二、六大设计原则（SOLID + LoD）

设计模式不是凭空发明的，它们都遵循六大面向对象设计原则。理解原则比背模式更重要——模式是”术”，原则是”道”。

1、单一职责原则（Single Responsibility Principle, SRP）

一个类应该只有一个引起它变化的原因。

2、开闭原则（Open-Closed Principle, OCP）

软件实体应该对扩展开放，对修改关闭。

这是设计模式的核心目标——不改老代码，只加新代码就能扩展功能。策略模式、观察者模式、装饰器模式都是 OCP 的经典实现。

3、里氏替换原则（Liskov Substitution Principle, LSP）

子类对象必须能够替换其父类对象，且程序行为不变。

经典反例：子类重写父类方法时抛出了父类不会抛出的异常，或改变了预期行为。Square 继承 Rectangle 但 setWidth 行为不同就是典型违反 LSP。

4、接口隔离原则（Interface Segregation Principle, ISP）

客户端不应该依赖它不需要的接口。

5、依赖倒置原则（Dependency Inversion Principle, DIP）

高层模块不应依赖低层模块，二者都应依赖抽象。抽象不应依赖细节，细节应依赖抽象。

Spring 的 IoC 容器就是 DIP 的终极实践——通过依赖注入，让业务代码只依赖接口，不依赖具体实现。

6、迪米特法则（Law of Demeter, LoD / 最少知识原则）

一个对象应该对其他对象保持最少的了解。只和”直接朋友”通信。

三、创建型模式（5 种）——关注”怎么创建对象”

1、单例模式（Singleton）

意图：确保一个类只有一个实例，并提供全局访问点。

七种写法对比

面试必问：volatile 的作用？——防止 new 对象时的指令重排（分配内存 → 调用构造 → 引用赋值 可能被重排为 分配 → 引用赋值 → 构造，导致其他线程拿到未初始化的对象）。

JDK 中的单例：java.lang.Runtime#getRuntime() 就是饿汉式单例。

2、工厂方法模式（Factory Method）

意图：定义创建对象的接口，让子类决定实例化哪个类。

Spring 中的应用：BeanFactory 就是工厂模式的体现，getBean() 方法根据名称/类型返回对应的 Bean。

3、抽象工厂模式（Abstract Factory）

意图：提供一个创建一系列相关或相互依赖对象的接口，无需指定具体类。

工厂方法 vs 抽象工厂：工厂方法生产一种产品（一维），抽象工厂生产一族产品（二维）。

4、建造者模式（Builder）

意图：将复杂对象的构建与表示分离，使同样的构建过程可以创建不同的表示。

JDK 中的应用：StringBuilder、StringBuffer、Stream.Builder、OkHttpClient.Builder。

5、原型模式（Prototype）

意图：通过拷贝现有实例来创建新对象，避免重复初始化开销。

深拷贝 vs 浅拷贝：浅拷贝只复制引用，深拷贝递归复制所有引用对象。super.clone() 是浅拷贝，需要手动处理引用类型字段。

四、结构型模式（7 种）——关注”怎么组合类和对象”

1、适配器模式（Adapter）

意图：将一个类的接口转换成客户端期望的另一个接口，使不兼容的类可以协作。

JDK 中的应用：java.io.InputStreamReader 就是适配器，把 InputStream（字节流）适配成 Reader（字符流）。

2、装饰器模式（Decorator）

意图：动态地给对象添加额外职责，比继承更灵活。

JDK 中的应用：java.io 包是装饰器模式的教科书——BufferedInputStream 装饰 FileInputStream，DataInputStream 再装饰 BufferedInputStream。

装饰器 vs 代理：装饰器侧重”增强功能”（调用者知道有装饰），代理侧重”控制访问”（调用者不知道有代理）。

3、代理模式（Proxy）

意图：为其他对象提供代理以控制对这个对象的访问。

Spring 中的应用：

  • JDK 动态代理：目标类实现接口时使用，基于 Proxy.newProxyInstance
  • CGLIB 代理：目标类没有接口时使用，通过生成子类实现
  • @Transactional、@Async、@Cacheable 等 AOP 注解的底层都是动态代理

4、外观模式（Facade）

意图：为子系统中的一组接口提供一个统一入口，降低子系统使用复杂度。

Spring 中的应用：JdbcTemplate 就是 JDBC 的外观模式——把 Connection、Statement、ResultSet 的复杂操作封装成一个简单方法调用。

5、桥接模式（Bridge）

意图：将抽象部分与实现部分分离，使它们可以独立变化。

6、组合模式（Composite）

意图：将对象组合成树形结构，使单个对象和组合对象的使用方式一致。

7、享元模式（Flyweight）

意图：共享细粒度对象，减少内存消耗。

JDK 中的应用：

  • Integer.valueOf(-128~127) 使用了享元模式，缓存了 -128 到 127 的 Integer 对象
  • String 常量池也是享元模式的体现

五、行为型模式（11 种）——关注”对象之间怎么通信”

1、策略模式（Strategy）

意图：定义一系列算法，封装每个算法并使它们可互换。消灭 if-else 的利器。

Spring 中的应用：Spring 用策略模式消除 if-else 的经典套路——将所有策略实现类注入到 Map 中，按 key 获取：

2、观察者模式（Observer）

意图：定义对象间一对多依赖，当一个对象状态变化时，所有依赖者自动收到通知。

Spring 中的应用：@EventListener + ApplicationEventPublisher 就是观察者模式。Spring Boot 的事件机制（ApplicationReadyEvent 等）也基于此。

3、模板方法模式（Template Method）

意图：定义算法骨架，将某些步骤延迟到子类实现。

Spring 中的应用：

  • JdbcTemplate：execute 方法是模板，PreparedStatementCallback 是可变步骤
  • RestTemplate、JmsTemplate、RedisTemplate 全家桶都是模板方法
  • AbstractApplicationContext#refresh() 是 Spring 启动流程的模板方法

4、责任链模式（Chain of Responsibility）

意图：将请求沿着处理者链传递，每个处理者决定处理或传给下一个。

Spring 中的应用：

  • Spring Security FilterChain：请求依次经过安全过滤器链（认证 → 授权 → CSRF → CORS）
  • Spring Interceptor：HandlerInterceptor 的 preHandle / postHandle 链
  • Netty ChannelPipeline：入站/出站事件沿 ChannelHandler 链传递
  • Servlet FilterChain：每个 Filter 调用 chain.doFilter() 传递给下一个

5、状态模式（State）

意图：允许对象在内部状态改变时改变其行为，看起来像换了类一样。

策略 vs 状态：策略模式由客户端选择策略（外部控制），状态模式由对象内部状态自动切换行为（内部驱动）。

6、命令模式（Command）

意图：将请求封装成对象，实现请求的参数化、排队、记录日志和撤销。

Spring 中的应用：Spring Batch 的 ItemReader / ItemProcessor / ItemWriter 接口就是命令模式的变体。

7-11、其余行为型模式速览

模式 意图 JDK/Spring 应用场景
迭代器模式 顺序访问集合元素，不暴露内部结构 Iterator 接口、增强 for 循环

七、2026 新趋势：AI Agent 设计模式

2026 年，随着 AI 编程和大模型应用的爆发，AI Agent 设计模式已成为面试新热点。传统 GoF 模式解决的是”代码组织”问题，而 Agent 模式解决的是”大模型推理与行动”问题。

八、10 道高频面试题

Q1：单例模式中 volatile 的作用是什么？

答：在双重检查锁（DCL）中，new Singleton() 不是原子操作，分为三步：①分配内存 ②调用构造方法 ③引用赋值。不加 volatile 时，JVM 可能将②③重排序为①③②，导致其他线程在②未完成时就拿到了引用，使用到未初始化的对象。volatile 通过内存屏障禁止指令重排，保证线程安全。

Q2：JDK 动态代理和 CGLIB 代理的区别？

维度 JDK 动态代理 CGLIB 代理
原理 基于接口，Proxy.newProxyInstance 基于继承，生成子类
要求 目标类必须实现接口 目标类不能是 final 类
性能 创建快，调用稍慢 创建慢，调用快
Spring 选择 有接口时默认使用 无接口时使用，或 proxyTargetClass=true

Q3：策略模式和状态模式的区别？

  • 策略模式：客户端主动选择策略，策略之间相互独立，不感知彼此存在
  • 状态模式：对象内部状态自动切换，状态之间知道如何流转到下一个状态
  • 一句话区分：策略是”你选哪个算法”，状态是”对象处于哪个阶段”

Q4：装饰器模式和代理模式的区别？

  • 装饰器：侧重增强功能，装饰器和被装饰者实现同一接口，客户端通常知道装饰过程
  • 代理：侧重控制访问，代理对象控制对真实对象的访问，客户端通常不知道代理存在
  • 一句话区分：装饰器是”加功能”，代理是”加控制”

Q5：工厂方法模式和抽象工厂模式的区别？

  • 工厂方法：生产一种产品，一个工厂对应一个产品
  • 抽象工厂：生产一族产品，一个工厂可以创建多个相关产品
  • 判断标准：产品是一维（单产品线）用工厂方法，产品是二维（多产品族×多产品等级）用抽象工厂

Q6：Spring 中用了哪些设计模式？至少说出 5 个。

  1. 单例：Bean 默认作用域为 singleton
  2. 工厂：BeanFactory 和 FactoryBean
  3. 代理：AOP 的 JDK 动态代理和 CGLIB 代理
  4. 模板方法：JdbcTemplate、RestTemplate、TransactionTemplate
  5. 观察者：ApplicationEventPublisher + @EventListener
  6. 责任链：Spring Security FilterChainProxy、MVC HandlerInterceptor
  7. 适配器：HandlerAdapter 适配不同类型的 Controller

Q7：如何用设计模式消除大量的 if-else？

Q8：建造者模式和工厂模式的区别？

  • 工厂模式：关注创建什么，一次创建一个完整对象
  • 建造者模式：关注怎么创建，分步骤构建复杂对象，支持灵活配置
  • 判断标准：对象参数少且固定用工厂，参数多且大部分可选用建造者

Q9：什么是开闭原则？哪个模式最能体现？

开闭原则（OCP）：对扩展开放，对修改关闭。策略模式最能体现——新增策略只需新增实现类，无需修改已有代码。观察者模式（新增观察者不改 Subject）和装饰器模式（新增装饰器不改被装饰者）也充分体现了 OCP。

Q10：什么是 AI Agent 设计模式？ReAct 模式的核心是什么？

AI Agent 设计模式是 2026 年面试新热点，解决大模型推理与行动的编排问题。ReAct（Reasoning + Acting） 是最经典的模式：LLM 交替进行推理（Thought）和行动（Action），每次行动后观察结果（Observation）并决定下一步，形成 Thought → Action → Observation 循环，直到得出最终答案。

九、生产避坑清单

  1. 不要为了用模式而用模式——简单 if-else 只有 2-3 个分支时，引入策略模式反而增加复杂度。模式是手段不是目的，YAGNI（You Aren’t Gonna Need It）原则优先。
  2. 单例不是全局变量——滥用单例会导致状态难以测试、隐藏依赖关系。能用 Spring DI 注入就不要手写单例。
  3. 装饰器层数不要太深——3 层以上的装饰器嵌套会让调试变成噩梦，考虑用组合或 AOP 替代。
  4. 代理模式注意性能——CGLIB 生成子类比 JDK 代理慢，但方法调用更快。高频调用的场景选 CGLIB，低频选 JDK。
  5. 观察者注意内存泄漏——观察者注册后忘记取消注册，导致对象无法被 GC。Spring @EventListener 没有这个问题，但手动实现时务必提供 unsubscribe。
  6. 责任链长度控制——链太长会影响性能（每个请求都遍历整条链），考虑用 Map 直接定位处理器。
  7. 模式组合使用——生产级代码往往组合多种模式。例如 Spring Security = 责任链（FilterChain）+ 策略（AuthenticationProvider）+ 代理（FilterInvocation）+ 模板方法（AuthenticationManager）。

十、总结

设计模式是后端工程师的基本功，核心价值在于：

  • 代码质量：遵循 SOLID 原则，写出可维护、可扩展的代码
  • 面试通关：设计模式 + Spring 源码 = 中高级面试必备组合
  • 架构思维：从”写代码”升级到”设计系统”
  • AI 时代：传统 GoF 模式 + Agent 设计模式 = 2026 后端核心竞争力

学习路径建议：

  1. 先理解六大原则（SOLID），这是”道”
  2. 重点掌握 8 种高频模式：单例、工厂、建造者、代理、装饰器、策略、观察者、模板方法
  3. 在 Spring/MyBatis 源码中找模式，加深理解
  4. 在项目实战中用模式，从”知道”变成”会用”
  5. 关注 AI Agent 设计模式新趋势，保持技术敏感度
