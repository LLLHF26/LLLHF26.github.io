ClickHouse 详解：从列式存储到实时分析与 2026 生产实战

发表于 2026-08-02 分类于 学习笔记

ClickHouse 是俄罗斯 Yandex 开源的列式在线分析处理（OLAP）数据库，以单机每秒数亿行的扫描速度和极致的压缩比闻名全球。在实时数仓、日志分析、用户行为分析、时序数据、A/B 测试报表等场景中，ClickHouse 已经取代传统 Hadoop/Spark 批处理方案，成为“准实时 OLAP”的事实标准。本文从列式存储原理出发，系统讲清 MergeTree 引擎家族、稀疏索引、向量化执行、分布式表、物化视图、Projection 等核心机制，并给出 Spring Boot 完整集成代码、2026 年 25.x/26.x 新特性解读与 10 条生产避坑清单。读完这篇，你能独立设计 ClickHouse 实时数仓、写出生产级查询与写入代码、在面试中讲清“为什么 ClickHouse 比 MySQL 快 100 倍”。

ClickHouse 详解：从列式存储到实时分析与 2026 生产实战

一、为什么需要 ClickHouse？OLAP 与 OLTP 的本质分野

1.1 行存与列存：两种截然相反的设计哲学

传统关系型数据库（MySQL、PostgreSQL）采用行式存储，一行数据在磁盘上连续存放。这种设计对 SELECT * WHERE id = ? 这类点查非常友好，因为只需一次 I/O 就能读完整行。但在分析型场景里，典型查询是：

这种查询只关心 country、amount、dt 三列，行存数据库却要先把整行读到内存再过滤，90% 以上的 I/O 都被浪费了。

列式存储把同一列的数据连续存放，带来三大收益：

收益 说明 典型效果
只读所需列 查询 3 列只需读 3 列，无需加载整行 I/O 降低 5-20 倍
同类型数据压缩率高 一列内数据类型相同，字典编码、Delta、Run-Length 压缩效果显著 压缩比 5-30 倍
向量化执行 列数据以数组形式批量交给 SIMD/CPU Cache 处理 单核吞吐提升 10-50 倍

维度 MySQL Elasticsearch ClickHouse
定位 OLTP 事务型数据库 搜索引擎 + 日志分析 OLAP 分析型数据库
存储模型 行存 B+Tree 倒排索引 + DocValues 列存 MergeTree
最佳场景 高并发点查、事务 全文检索、日志检索 聚合分析、时序数据、宽表分析

JOIN 能力 强 弱 有限，推荐大表 JOIN 小表

选型决策树：

  • 需要 ACID 事务、高并发行级更新 → 选 MySQL/PostgreSQL
  • 需要 全文检索、模糊查询、日志关键词搜索 → 选 Elasticsearch
  • 需要 海量数据聚合、实时报表、时序分析、低成本存储日志/埋点 → 选 ClickHouse

2.2 列式 Block：向量化执行的最小单元

ClickHouse 内部数据以 Block 为单位流动。一个 Block 是一组列的集合，每列是一个连续数组。执行器对 Block 进行批量操作，而不是逐行处理：

向量化执行的优势：

  1. CPU Cache 友好：连续内存访问，命中率远高于随机行存
  2. SIMD 加速：一条指令处理 256/512 bit 数据，如 sum()、avg()
  3. 分支预测友好：同类型数据批量处理，条件判断少
  4. 编译器自动优化：更容易触发循环展开、向量化指令生成

2.3 MPP 与 Shared-Nothing

ClickHouse 集群采用 Shared-Nothing 架构：每个节点独立存储、独立计算。查询通过分布式表（Distributed Table）路由到多个分片，各分片并行计算后由发起节点汇总。这种设计水平扩展性极强，增加节点即可线性提升吞吐。

三、MergeTree 存储引擎：ClickHouse 的灵魂

3.1 为什么叫 MergeTree？

MergeTree 是 ClickHouse 最核心的表引擎，名字来源于后台持续进行的 Merge（合并） 操作：数据写入时先形成一个个不可变的 Part（数据片段），后台线程按规则合并小 Part 为大 Part，同时进行去重、TTL 清理、索引优化。

这种 LSM-Tree 风格 的设计带来三个特性：

  • 高吞吐写入：顺序追加，避免随机 I/O
  • 不可变 Part：没有行锁，没有 MVCC 开销
  • 后台合并：查询性能随合并逐渐稳定

3.3 主键与稀疏索引

ClickHouse 的主键不是 MySQL 意义上的唯一约束，而是排序键（Sorting Key）。数据按主键列在 Part 内有序存放，并每隔 index_granularity 行（默认 8192）生成一个主键索引条目，这就是稀疏索引。

查询时，ClickHouse 先用主键索引定位到可能的 Granule，再解压对应数据块进行过滤。稀疏索引非常轻量，即使百亿行数据，主键索引也能完全放入内存。

3.4 分区（Partition）与分桶

概念 作用 建议
PARTITION BY 按时间/业务维度切分数据，查询时只扫描相关分区 时间序列表按 toYYYYMMDD(dt) 或 toYYYYMM(dt) 分区
ORDER BY 定义数据在 Part 内的排序方式，决定稀疏索引效率 把最常用的过滤列放在前面
PRIMARY KEY 默认与 ORDER BY 一致，可指定前缀索引 通常无需单独设置
SAMPLE BY 采样键，用于近似查询 日志/埋点类大表建议设置

最佳实践：

  • 分区粒度不要太细，避免 Part 过多（建议单表 Part 数 < 10 万）
  • ORDER BY 第一列通常是时间或业务主键，保证查询能命中索引
  • 避免在高基数列上分区（如 PARTITION BY user_id 会导致海量小 Part）

3.5 二级索引与数据跳过索引

除了主键稀疏索引，ClickHouse 还提供 Skip Index（数据跳过索引），在 25.12 中进一步增强了 Top-N 场景的跳过能力。

常见 Skip Index 类型：

索引类型 用途 示例
minmax 记录每段 granule 的 min/max 范围查询加速
set 记录每段 granule 内 distinct 值集合 IN 查询加速
bloom_filter 布隆过滤器判断值是否可能存在 等值查询加速
tokenbf_v1 对字符串分词后建布隆过滤器 LIKE '%keyword%' 加速
ngrambf_v1 n-gram 布隆过滤器 子串搜索加速

ReplicatedMergeTree 依赖 ZooKeeper 或 ClickHouse Keeper 协调副本：

  1. 一个 Part 写入主副本后，记录到 ZooKeeper 的日志队列
  2. 其他副本拉取日志，下载 Part 到本地
  3. 后台合并操作也会在副本间同步

2026 年趋势：越来越多公司用 ClickHouse Keeper（C++ 实现）替代 ZooKeeper，降低内存和 I/O 开销 4-8 倍。

十一、生产避坑：10 条血泪经验

  1. 不要用 ClickHouse 做 OLTP：高频单行更新、强事务、外键需求请用 MySQL/PostgreSQL
  2. 分区粒度要合理：按小时分区会导致 Part 爆炸，按年分区又失去裁剪意义
  3. ORDER BY 不要放高基数 UUID 第一列：否则索引失效，查询变全表扫描
  4. 写入失败不要盲目重试：重复写入会导致 ReplacingMergeTree 去重压力增大
  5. JOIN 要控制右表大小：大表 JOIN 大表会触发内存溢出或分布式 JOIN 风暴
  6. 慎用 FINAL 和 GLOBAL：FINAL 会强制实时去重，性能开销大；GLOBAL 会广播右表
  7. String 列尽量转 LowCardinality：枚举类字符串可节省 5-10 倍存储并加速分组
  8. TTL 要提前规划：数据过期策略应在建表时设计，避免后期 ALTER 大表锁操作
  9. 监控 Part 数量：单表 Part 过多会拖慢查询，可设置 max_parts_in_total 告警
  10. 生产必开查询日志：通过 system.query_log 持续慢查询治理，而不是出了问题再抓包

十二、高频面试题 8 道

1. ClickHouse 为什么这么快？

答：列式存储减少 I/O、同列数据压缩比高、向量化执行 + SIMD、稀疏索引轻量高效、MPP 分布式并行、LSM-Tree 顺序写入高吞吐。

2. MergeTree 的 Part 是什么？为什么后台要 Merge？

答：每次写入生成不可变 Part，后台 Merge 把小 Part 合并成大 Part，减少查询时需要扫描的文件数，同时执行去重、TTL、索引重建。

3. ClickHouse 的主键和 MySQL 主键有什么区别？

答：ClickHouse 主键是排序键，不保证唯一，决定数据在 Part 内的物理顺序；MySQL 主键是聚簇索引 + 唯一约束。

4. ReplacingMergeTree 如何去重？查询时需要注意什么？

答：按 ORDER BY 去重，保留版本号最大或最后写入的行。查询时需要加 FINAL 关键字才能保证实时去重，或依赖后台 Merge。

5. 分布式表写入有哪些方式？生产推荐哪种？

答：可通过 Distributed 表写入（简单但有单点瓶颈），或业务层按分片键直接写本地表（性能更高、更可控）。

6. ClickHouse 适合做实时更新吗？

答：不适合高频 OLTP 式更新。25.x 后 Lightweight Update/Delete 有所改善，但底层仍是“标记 + 合并”语义，适合低频批量修正。

7. Materialized View 和 Projection 有什么区别？

答：MV 是写入时触发到独立目标表的预计算；Projection 是同表数据的另一种排序/聚合视图，查询时优化器自动选择。

8. 设计一张日志分析表，你会怎么选分区、排序键和索引？

答：

  • 分区：PARTITION BY toYYYYMMDD(ts)，按天裁剪
  • 排序键：ORDER BY (ts, level, service)，满足时间范围 + 级别过滤
  • 索引：对 message 建 tokenbf_v1 或 ngrambf_v1 加速关键词检索
  • 类型：枚举列用 LowCardinality，JSON 字段用 JSON 类型（25.x+）

结语

ClickHouse 不是 MySQL 的替代品，而是 OLAP 场景下的“专用赛车”。理解列存、MergeTree、稀疏索引、向量化执行这四根支柱，你就掌握了 ClickHouse 的设计精髓。2026 年，随着 Lightweight Update/Delete、QBit 向量、Arrow Flight、地理空间类型等特性的成熟，ClickHouse 正从“纯分析数据库”向“实时数据平台”演进。如果你的业务涉及海量日志、埋点、时序、实时报表，现在正是把 ClickHouse 纳入技术栈的最佳时机。
